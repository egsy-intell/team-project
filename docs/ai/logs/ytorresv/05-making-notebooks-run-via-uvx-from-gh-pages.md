### Claude

Two different levels of "generic" here, worth separating:

**The publishing/launching mechanics — yes, fully generic.** `scripts/export_notebooks.py` globs every `*.py` in `notebooks/`, exports HTML, and copies the raw source for each. `scripts/run_notebook.sh <notebook-name> [edit|run]` accepts any name. So the moment you add `notebooks/foo.py`, it gets published to `docs/notebooks/foo.py` and `scripts/run_notebook.sh foo` just works — nothing hardcoded there.

**The self-healing data/import fallback — no, that's per-notebook, not automatic.** I only added the "if local data isn't there, download it" and "if the sibling module isn't there, fetch it" logic inside `checkpoint_1.py` and `data_dictionary.py` specifically. A new notebook you add later would need:

- Its own PEP 723 header (deps it actually imports), and
- The same kind of existence-check-then-download fallback, *if* it reads from `data/` or imports another notebook file as a submodule.

A notebook with no local data/sibling dependencies (pure computation, or one that only pulls from a public URL already) would work via `uvx` out of the box with zero extra code — just the PEP 723 header.

So: the pipeline (export → publish → launch) works for any notebook automatically; the "make it runnable with no local files" trick only works for notebooks that either don't need local files, or that get the same fallback pattern added by hand. If you're planning more notebooks that touch `data/`, I could factor that fallback into a small shared snippet you paste into each new one (a true shared helper module can't easily be reused since the import problem is the same download problem), rather than leaving it fully ad hoc.
